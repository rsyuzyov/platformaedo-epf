# Платформа ЭДО — внешняя обработка с исправлениями (неофициальный репозиторий)

Внешняя обработка «Платформа ЭДО» (`ОФД_ЭДО`) для обмена электронными документами через оператора
[Платформа ОФД](https://platformaofd.ru) из типовых конфигураций 1С (Бухгалтерия 3.0, УТ 11, ERP, КА,
Розница, УНФ). Здесь лежит обработка вендора и наши исправления к ней.

⚠️ **Репозиторий неофициальный.** Его ведут пользователи обработки, а не вендор. Оригинал публикует
вендор: <https://platformaofd.ru/pdf/edo-files/ofd-edo.rar>. Публикация согласована с вендором.

## Чем отличается от обработки вендора

Все отличия видны одним сравнением: [`vendor...main`](../../compare/vendor...main).
Список исправлений — в [релизах](../../releases).

## Ветки

| ветка | что в ней |
|---|---|
| `vendor` | только обработка вендора, без единой правки: по коммиту и тегу `vendor/<версия>` на каждую версию |
| `main` | обработка вендора плюс наши исправления |

- Что изменил вендор между своими версиями: `git diff vendor/1.0.5.3.8 vendor/<новая> -- src`.
- Наши правки поверх вендора: `git diff vendor main -- src`.
- В `main` и `vendor` напрямую не пушим, только через pull request.

## Исходники

`src/` — XML-выгрузка обработки в **формате 2.14 (платформа 8.3.21)**. Формат выбран намеренно старым:
исходники загружает и собирает любая платформа 8.3.21 и новее, а собранный файл открывается у всех,
кто на 8.3.21 и выше.

⚠️ Выгружать и собирать только платформой **8.3.21**. Конфигуратор пишет формат своей версии:
выгрузка из 8.3.27 даст 2.20, из 8.5 — 2.21, и дифф утонет в изменениях формата. `build/build.ps1`
и проверки в CI сверяют формат и откажутся пропускать чужой.

## Версии

Версия обработки = версия вендора + номер нашей сборки: `1.0.5.3.8.1`, `1.0.5.3.8.2` и т. д. Хранится там же,
где у вендора, — в `СведенияОВнешнейОбработке()` модуля объекта, её видно в карточке дополнительной обработки.

- Номер сборки растёт при **каждом** изменении `src/`: две разные сборки с одним номером неотличимы.
- После слияния новой версии вендора база меняется на его номер, а счётчик начинается с 1.
- Релиз — тег `v<версия>` и `.epf` в GitHub Releases с sha256.

`build/checks.py` (запускается в CI на каждый PR) проверяет: формат выгрузки 2.14, версию на базе последнего
влитого тега `vendor/*`, рост версии при изменении `src/`, разбор XML, BOM текстовых макетов и отсутствие
в коде адресов, паролей и отпечатков сертификатов.

## Сборка

Нужна только платформа 8.3.21 (толстый клиент с конфигуратором), рабочая база не нужна:

```powershell
.\build\build.ps1            # -> dist\Платформа_ЭДО_<версия>.epf, в конце печатает sha256
```

Если платформа стоит не в `C:\Program Files\1cv8\8.3.21.1895`, путь к `1cv8.exe` передаётся в `-Designer`.

## Новая версия вендора

1. Скачать `ofd-edo.rar` с сайта вендора.
2. Сделать вторую рабочую копию на новой ветке от `vendor`:
   `git worktree add ..\pedo-vendor -b vendor-import/<версия> origin/vendor`.
3. Из рабочей копии `main` запустить импорт:
   `.\build\vendor-import.ps1 -Root ..\pedo-vendor -Source <путь>\ofd-edo.rar -Version <версия>`.
   Скрипт заменит `src/` выгрузкой вендора и напечатает команду коммита.
4. PR `vendor-import/<версия>` → `vendor`, после слияния — тег `vendor/<версия>`.
5. PR `vendor` → `main`. Конфликты слияния — ровно те места, где вендор менял то же, что и мы.

Импорт выгружает обработку, собирает её и выгружает ещё раз. Платформа при сборке переставляет
порядок обработчиков в некоторых формах, и без второго круга эта перестановка всплыла бы шумом в первом
же PR, где форму выгрузили из конфигуратора.

## Как предложить исправление

Ветка от `main` → правка в `src/` → номер сборки +1 (см. «Версии») → проверка `build/build.ps1`
и `python build/checks.py` → pull request в `main`.
Один PR — одно исправление, в описании: что ломалось, как воспроизвести, что изменено.
